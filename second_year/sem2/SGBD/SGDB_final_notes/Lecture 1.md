
# Concurrency

## 1. ACID:

#### A -> atomicity: the transaction either commits if everything succeeds, or rolls back if ANYTHING is wrong or crashed inside the transaction -> it works like a non-separable unit, its either one or the other

#### C -> consistency: the DB is consistent before and after the transaction -> it basically means that the transaction follows the right syntax and the constraints o the DB, it does not break them (the transaction should be written correctly, in short)

#### I -> isolation: even if multiple transaction run in parallel, one should be able to look at transaction T as if it's running separately of the others (concurrency does not affect the result of the transaction, and it works the same as if it would run alone, separately of potential other transactions)

### D -> durability: if a transaction succeeds, its results must be stored on the disk even if a crash would happen before that

## 3.Interleaved Executions Anomalies

#### T1 and T2 are both reading => no conflict

#### T1 and T2 are reading/writing completely different data => no conflict

#### T1 and T2 operating on the same data object and at least one of them performs a write => order of execution is important:
	• WR conflict (aka dirty reads): T2 is reading a data object previously written by T1 
	• RW conflict (aka unrepeatable read): T2 is writing a data object previously read by T1 
	• WW conflict: T2 is writing a data object previously written by T1

## 4. Serializability

#### C -> set of transactions, Sch(C) -> set of schedules for C

Serializable Schedule:
#### a schedule S ∈ Sch(C) is serializable if the effect of S on any consistent database instance is identical to the effect of some serial schedule S0 ∈ Sch(C) 

#### Serializability = correctness criterion for an interleaved (serial) schedule 

#### Ensuring serializability prevents inconsistencies that may be generated by concurrent transactions interfering with one another.

#### Serializability is basically the database saying:
> "I'll let transactions run concurrently for performance, but I promise the end result will look as if they ran one at a time."
